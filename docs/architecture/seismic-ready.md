# Архитектура: готовность к сейсмике

> Статус: план / проектное решение. Обсуждено 2026-08-07.
> Область: как расти к сейсмике (и 3D) без переписывания текущего продукта.

## Контекст

GeoViewer сейчас закрывает **карточный (2D) тракт геомоделирования**:
данные → корреляция → структурные карты (TVD) → net pay из логов → подсчёт
запасов (ВНК, P90/P50/P10) → сводка по пластам → кроссплоты. Сейсмика, 3D-геосетка,
фациальное/свойственное моделирование и разломы — **вне текущего клина** (см. карту
покрытия в руководстве пользователя).

Вопрос: как спроектировать архитектуру, чтобы добавить сейсмику позже без
переписывания того, что уже работает.

## Решение (вердикт)

**Модульный монолит с общим доменным ядром.** Не два отдельных продукта.
Тяжёлые внутренности сейсмики изолируем за интерфейсом, но **интегрируем на уровне
геологической модели** (структурный каркас). Сейсмика — это модуль-источник,
который вставляется в общий каркас, а не параллельная вселенная.

### Почему не два раздельных продукта

Разделить в ноль убьёт саму ценность — смысл геомоделирования в **интеграции**
скважин и сейсмики в одну модель. Они обязаны делить:

- систему координат / датум / время↔глубину (иначе «скважины в одном CRS, куб в другом»);
- скважины видны на сейсмике; горизонты с сейсмики ложатся в **те же** структурные
  поверхности, что и пикировки скважин;
- разломы, зоны, проект — общие.

## Целевая архитектура — три слоя

```
┌────────────────────────────────────────────────────────────┐
│  Оболочка приложения — вкладки · проекты · один деплой       │
└────────────────────────────────────────────────────────────┘

  Источники данных                         (модули изолированы
  ┌──────────────┐        ┌──────────────┐  друг от друга)
  │  Скважины    │        │  Сейсмика     │  ← позже
  │  LAS·петрофиз│        │  SEG-Y·WebGL  │
  └──────┬───────┘        └──────┬───────┘
         │                       ┆ (пунктир = будущее)
         └──────────►  ЯДРО  ◄───┘
                 ┌─────────────────────────────────┐
                 │  Структурный каркас — точка      │
                 │  интеграции: Surface·Horizon·    │
                 │  Fault (несколько источников)    │
                 │  ─────────────────────────────── │
                 │  Проект · CRS/датум/единицы·зоны  │
                 └──────────────┬──────────────────┘
                                │
        ┌───────────────┬───────┴───────┬───────────────┐
        ▼               ▼               ▼
   ┌─────────┐     ┌─────────┐     ┌───────────┐
   │  Карты  │     │ Запасы  │     │ Кроссплоты│
   └─────────┘     └─────────┘     └───────────┘
   потребители читают каркас, не лезут в скважины напрямую
```

- **App shell** — вкладки, layout, проекты, роутинг. Композирует модули.
- **Feature-модули (bounded contexts)** — `wells`, `seismic` (позже), `maps/surfaces`,
  `volumetrics`, `petrophysics`. Каждый владеет своим вводом данных, тяжёлым
  compute и рендером.
- **Core / ядро (shared kernel)** — общая правда, чистый TS, без UI и рендера:
  `Project`, CRS/units/datum, **структурный каркас** (`Surface`/`Horizon`/`Fault`), зоны.

### Правило зависимостей

Модули зависят **только от ядра**, не друг от друга. `seismic` не импортирует из
`wells` и наоборот — общаются через доменные объекты ядра. Защитить линтером границ
(dependency-cruiser / eslint import boundaries), иначе связи сгниют.

## Ключевое решение (одно, самое важное)

**Структурный каркас — точка интеграции.** Сделать `Surface` / `Horizon` / `Fault`
первоклассными доменными объектами с **несколькими источниками данных**:

```
Surface "Top A"
  ├─ control: well picks       (сейчас)
  ├─ control: seismic horizon  (потом)
  └─ grid: построен из ВСЕХ источников
```

Сейчас `WellMap` берёт маркеры и гридит их IDW «на месте» — это будущая ловушка.
Правильно: карта — **потребитель `Surface`**, а не гриддер маркеров. Появляется
сервис `buildSurface(controls)` (скважины сегодня, +сейсмика завтра). Одно это
решение отделяет от переписывания.

## Технические границы сейсмики

Сейсмика тяжёлая и живёт **за интерфейсом**:

- Данные: **SEG-Y = гигабайты**, в память/IndexedDB не влезет → стриминг/тайлинг,
  декодирование в **WASM + Web Workers**, крупные кубы — **бэкенд**.
- Рендер: **WebGL/GPU** (canvas 2D для куба не потянет). Разные рендереры по модулям —
  это нормально (скважины: canvas 2D; карты: canvas+SVG; сейсмика: WebGL).
- Остальной апп общается с модулем тонким API: «дай горизонт как `Surface`»,
  «нарисуй inline N», «переведи время↔глубину».
- Вывод: сейсмика **форсит облако/бэкенд** — стыкуется с отложенным шагом «SaaS».

Куда сейсмика подключается в цикле: её продукты — горизонты (→ структурный каркас,
этап 4), разломы (→ fault framework, этап 6), привязка скважина-сейсмика и
время↔глубина. Это **источник данных для каркаса**, идущий до/параллельно, а не
после.

## Что делать СЕЙЧАС vs ПОТОМ

**Сейчас** (дёшево, не уходя в сейсмику — держим клин; 3 шва):

1. **Каркас как домен.** Ввести `Surface`/`Horizon`/`Fault` с источниками; вынести
   гридинг из `WellMap` в сервис `buildSurface(controls)`; карта — потребитель
   `Surface`. → новый `src/core/framework/`.
2. **CRS в ядро.** Сейчас `well.x/y` — сырые метры без системы координат. Завести
   `src/core/crs` (координаты, датум, единицы, время↔глубина).
3. **Разложить по доменам + слайсы стора.** Из `src/geo`+`src/las`+один Zustand-стор
   → `src/core`, `src/wells`, (позже) `src/seismic`; god-стор порезать на слайсы;
   границы импортов защитить линтером.

**Потом** (отдельный большой этап): сам модуль `seismic` + бэкенд. Вставляется в эти
швы **аддитивно**, не переписывая существующее.

> ⚠️ Не переусложнять сейчас. Полноценная плагин-система / микрофронты —
> преждевременно (YAGNI). Один репозиторий, один деплой; бэкенд для тяжёлого
> compute — отдельный сервис, но фронт остаётся одним интегрированным приложением
> с модулями.
